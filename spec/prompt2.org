*** Ambiguity in "slug part."
- Two readings:

1. *The URL path* — 'https://site.com/2026/05/my-post/' →
   '/2026/05/my-post/'
2. *Just the post_name* — 'https://site.com/2026/05/my-post/' →
   'my-post'

- Your "I.e. don't include the domain name" points at #1, so that's
  what I implemented. It also resolves more reliably on the round
  trip: 'fMcResolveUrl()' can hand a full path to 'url_to_postid()'
  and get an exact match, whereas a bare 'my-post' always falls
  through to 'fMcSlugToId()', which takes the lowest ID matching that
  'post_name' — so a post and a page sharing a slug, or a child page
  whose slug collides, would resolve to the wrong item. Say the word
  if you meant #2; it's a one-line change in the new function.

- Two judgment calls worth flagging:

- *I kept the query string.* If a site uses plain permalinks,
  'get_permalink()' returns 'https://site.com/?p=12', and taking only
  the path would collapse every post to '/' — the list would be
  useless and Delete would fail on all of it. Four lines prevent that,
  and 'fMcResolveUrl()' already has a '?p=' branch to catch it on the
  way back. Drop the '$tQuery' block if plain permalinks aren't a
  configuration you care about.

- *Percent-encoding is left alone.* A post titled "café" lists as
  '/caf%C3%A9/', which is what 'get_permalink()' returns and what
  resolves correctly. Decoding it would look nicer but risks a
  round-trip failure.
