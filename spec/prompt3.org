*** How it would work

- The natural place is 'fMcHandlePost()', in the 'delete' branch,
  *after* 'fMcDeleteUrls()' and alongside
  'fMcPurgeRevisions()'. Order matters: media that was only referenced
  by a deleted post has to become unreferenced before the scan runs.

- The scan itself would build a "used" set from whatever posts and
  pages survive:

1. Featured images ('_thumbnail_id').
2. Attachment IDs in content — 'wp-image-123' classes and '[gallery
   ids="..."]'.
3. Filename matches. This is the part that has to be a heuristic:
   content references 'photo-300x200.jpg' or 'photo-scaled.jpg', not
   the original 'photo.jpg'. Matching on the base filename catches all
   the generated sizes at once.

- Then 'wp_delete_attachment($tId, true)' on everything not in that
  set, which removes the file and all its generated sizes.

*** What I want to flag before writing it

- The filename match is fuzzy by design, and I'd deliberately bias it
  toward *false "used"* — an attachment named '1.jpg' or 'logo.png'
  will match almost anything and get kept. That's the safe direction,
  since the alternative is permanent file deletion. You should expect
  this to leave some genuinely-unused files behind rather than trust
  it to be exhaustive.

- Also out of scope unless you say otherwise: orphaned files sitting
  in 'wp-content/uploads' with no Media Library record. Deleting those
  means walking the filesystem, and that directory also holds backups,
  cache, and plugin-generated files. Too dangerous to sweep blind.

- Three decisions I don't want to make silently:

1. An image uploaded to a surviving post (post_parent points at it)
   but never actually inserted into its content — used or not?
   + Delete it (only content references count)
2. What should count as "used"? Media can also be referenced by the
   site logo, site icon, header/background image, and custom post
   types.
   + Posts and pages + protect site logo/icon/header
3. The plugin's whole workflow is review-then-delete. Should media get
   the same treatment?
   + Just delete, report the count after

*** Two things to know before running it

*** Tightened 'fMcFileInText()'.
- It was doing a bare 'strpos' on the filename with the extension
  stripped, so an image named 'home.jpg' counted as used if the word
  "home" appeared anywhere in any surviving page. Now the name has to
  be followed by its extension, with an optional size suffix in
  between. 'photo-300x200.jpg' and 'photo-scaled.jpg' still match; the
  word "photo" in a sentence no longer does.

*** New 'fMcSweepUploads()'.
- Walks the uploads tree and deletes any file no surviving attachment
  claims. 'fMcKeptFiles()' builds that claim set from
  'get_attached_file()' plus every entry in '_wp_attachment_metadata'
  — sizes and 'original_image' — plus '.webp'/'.avif' siblings, since
  optimizer plugins write those without telling WordPress. This is
  what catches manual FTP uploads, leftovers from long-deleted
  attachments, and stale thumbnail sizes from a previous theme.

*** Guards, since this deletes from disk directly

- Two allow-lists, both editable at the top of the new block:

- 'fMcMediaExt()' — only image, audio, video, and document extensions
  get deleted. '.php', '.htaccess', '.css', '.js', '.zip', and '.log'
  are never touched, which protects WordPress's index.php guards,
  Elementor's generated CSS, and backup archives.
- 'fMcSkipDirs()' — skipped whole. Includes 'sites', which matters on
  multisite: without it, running this on the main site would delete
  every other site's media.

- Symlinks are skipped rather than followed, so the sweep can't escape
  the uploads tree.
