** MakeCore plugin
+ Follow the directions in CLAUDE.org

+ Goal: Make a WordPress plugin that can be used to remove a lot of
  content so that a "core" WordPress site is ready to be handed off to
  others.

+ Plugin name: MakeCore

+ Initial version: 0.1

*** Settings Admin Page

+ Create an admin page with three text boxes, and two buttons.

+ "Keep Posts" Text box - This will be a list of post URLS, one per line,
  that will not be deleted. 

+ "Keep Pages" Text box - This will be a list of page URLS, one per line,
  that will not be deleted.

+ When the "List" button is clicked, the list of post and page URLs
  that will be deleted will be put in the "To Be Deleted" scrollable
  text box. In other words, this will be a list of all the posts
  and pages that are not in the Keep text boxes.

+ When the "Delete" button is clicked, an OK or Cancel message box
  will popup. If OK is pressed the posts and pages in the
  "To Be Deleted" box will be removed.

+ After pages and posts are deleted, remove all "revisions" from the
  remaining pages and posts.

** Response

- That skill targets standalone web UI; a WordPress admin screen
  should match core's admin styling instead, so I'm using native WP
  markup and classes. Writing the plugin now.Install by copying the
  'makecore' folder into 'wp-content/plugins/'.

- How it works, given your three answers:

*** Delete is permanent.
- 'wp_delete_post($tId, true)' — no trash, no undo. The confirm dialog
  and the on-page warning are the only guards.

*** Delete acts on the box.
- The textarea is editable and the handler parses whatever it
  contains, resolving each line independently. Blank lines and '#'
  comment lines are ignored, so you can annotate the list before
  deleting.

*** All statuses, including trash.
- 'fMcStatusList()' covers publish, future, draft, pending, private,
  and trash.

- Two implementation notes worth knowing about:

- 'url_to_postid()' only resolves published content, which would have
  made the "everything including trashed" answer unworkable on its
  own. So 'fMcResolveUrl()' tries three things in order: a
  'p='/'page_id=' query arg (which is what 'get_permalink()' returns
  for drafts), then 'url_to_postid()', then a direct slug lookup
  against 'wp_posts' in any status (which catches trashed items, whose
  slugs carry a '__trashed' suffix). If a slug is duplicated across
  two items, the lowest ID wins — an edge case I chose not to build UI
  around.

- Because the box is editable, a typo could in principle resolve to
  something you didn't mean. Delete therefore re-checks each ID's post
  type and refuses anything that isn't a post or page, and still
  honors the front page / posts page exclusion. Anything skipped is
  reported by URL in a warning notice rather than dropped silently.

  the package mirrors aren't reachable. Structure checks pass
  (balanced braces, no tabs, all lines under 79 chars), but run 'php
  -l makecore.php' before activating.

*** Assumptions

1. *Keep lists are now type-specific.* "Keep Posts" only protects
   posts, "Keep Pages" only protects pages. Previously the two boxes
   were merged before filtering, so a page URL typed into the wrong
   box still worked. Now it won't. Because the consequence is
   permanent deletion, I made a mismatch loud instead of silent: a URL
   in the wrong keep box gets reported in the "Skipped these lines"
   warning. It is still *not* kept. Say the word if you'd rather it be
   kept silently, or rather have no check at all.
2. *Sort is plain ascending string sort on the full permalink URL*
   (PHP 'sort()'), not by ID, title, or date.
3. *Delete still acts on both boxes together.* 'fMcDeleteUrls()'
   already validates type per URL, so it doesn't need to know which
   box a line came from. Putting a page URL in "Delete Posts" will
   still delete it. Tell me if Delete should reject cross-type lines
   instead.
4. Revision purge is unchanged — it still covers all remaining posts
   *and* pages.
